## 1. Top-Level Overview

ForgeGuard is an AI-powered software-change validation and release-readiness platform built to demonstrate how IBM Bob 2.0 can act as an engineering partner across a complete software-development lifecycle.

A developer submits an issue or change request. ForgeGuard drives Bob through a structured, auditable pipeline:

```
Issue / Change Request
  → Repository Understanding
  → Parallel Specialist Analysis (Code · Test · Security · API · Docs)
  → Unified Change Plan
  → Developer Approval
  → Implementation
  → Automated Validation (lint · tests · type-check)
  → Release Readiness Report
```

The frontend is a polished **engineering control-center UI** — not a chatbot.  
The backend orchestrates Bob 2.0 sessions and exposes a REST/WebSocket API.  
Bob 2.0 is the reasoning engine. All analysis, planning, and code work is done by Bob.

## 2. Recommended System Architecture

```
┌─────────────────────────────────────────────────────────┐
│                   Browser (React SPA)                   │
│  Sidebar · Pipeline Stepper · Evidence Panel · Diff View│
└────────────────────┬────────────────────────────────────┘
                     │ REST + WebSocket (streaming)
┌────────────────────▼────────────────────────────────────┐
│              ForgeGuard Backend (Node / Express)         │
│  PipelineController · SessionManager · ArtifactStore    │
└───┬──────────────────┬──────────────────────────────────┘
    │ Bob REST API      │ File System
┌───▼──────────┐  ┌────▼─────────────────┐
│  IBM Bob 2.0 │  │  Workspace / Repo     │
│  (Plan mode) │  │  (target codebase)    │
│  (Agent mode)│  │  e.g. demo-app/       │
└──────────────┘  └──────────────────────┘
```

**Key decisions:**
- Backend is Node.js + Express (fast to scaffold, good WebSocket support, matches Bob's JS ecosystem).
- Frontend is React + TypeScript with Tailwind CSS (rapid, polished UI).
- Bob 2.0 is accessed via its REST API (or CLI invocation) from the backend.
- All Bob sessions are recorded: prompts sent, responses received, artifacts generated.
- A lightweight SQLite database (via better-sqlite3) stores runs, artifacts, and evidence.
- The target "codebase under test" is a small, purpose-built demo application that lives in `demo-app/`.

## 3. MVP Scope

### In scope

- Submit an issue/change request through the UI
- Automated repository understanding phase (Bob analyzes demo-app/)
- Five parallel specialist analyses run as Bob subagents:
  1. Code Impact Analysis
  2. Test Engineering Analysis
  3. Security Analysis
  4. API/Compatibility Analysis
  5. Documentation Analysis
- Findings synthesized into a structured Change Plan (JSON + Markdown)
- Developer approval step in the UI (approve / request revision)
- Implementation phase: Bob (Agent mode) applies the change
- Validation phase: lint + unit tests run automatically, results captured
- Release Readiness Report generated by Bob
- Evidence panel showing every Bob interaction (prompts, responses, artifacts)
- Rollback: git-based (`git stash` or branch), one-click in UI
- Demo scenario: one pre-scripted bug fix + one pre-scripted feature addition

## 4. User Workflow

```
Step 1  │  Developer opens ForgeGuard UI
Step 2  │  Selects or pastes an issue description
Step 3  │  Clicks "Analyze"
Step 4  │  ForgeGuard runs Repository Understanding (Bob, Plan mode)
Step 5  │  Five specialist subagents run in parallel (visible in UI)
Step 6  │  Findings appear in real time on the Evidence Panel
Step 7  │  Bob synthesizes findings into a Change Plan
Step 8  │  Developer reviews the plan (diff preview, risk level, checklist)
Step 9  │  Developer clicks "Approve Plan" (or "Request Revision")
Step 10 │  ForgeGuard triggers Implementation (Bob, Agent mode)
Step 11 │  File diffs appear in real time as Bob writes code
Step 12 │  Validation runs automatically (lint, tests)
Step 13 │  Results displayed: pass/fail per test, security findings, compatibility
Step 14 │  Release Readiness Report rendered (risk · confidence · checklist)
Step 15 │  One-click Rollback available at all times after Step 10
```

## 7. Bob 2.0 Integration Strategy

Bob 2.0 is invoked by the backend at each pipeline phase. The integration pattern:

1. **Backend constructs a structured prompt** from a template + run context.
2. **Bob is invoked** (via REST API or CLI subprocess) in the appropriate mode.
3. **Bob's response is streamed** back to the frontend via WebSocket.
4. **Every prompt and response is stored** as an EvidenceItem in the database.
5. **Structured outputs** (JSON plans, test results, risk levels) are extracted from Bob's responses using delimited blocks (`--- FORGEGUARD:JSON ---`).

### Mode usage per phase

| Phase | Bob Mode | Why |
|---|---|---|
| Repository Understanding | Plan | Reason about structure before acting |
| Parallel Specialist Analysis | Plan (×5 subagents) | Independent reasoning per domain |
| Synthesize Change Plan | Plan | Structured output, no file writes yet |
| Implementation | Agent | File writes, code edits |
| Validation | Agent | Run lint/test commands, capture output |
| Release Report | Plan | Reason about evidence, no file writes |

### Subagent strategy

Each of the five specialist analyses is launched as an independent Bob Plan-mode session with:
- A specialist-specific system prompt (loaded from a Bob Skill)
- The repo summary as context
- The issue text as the change request
- Instructions to return structured JSON findings

All five run in parallel (Promise.all on the backend), and their durations are shown live in the UI — demonstrating Bob's parallel workstream capability.

### Skills used

Skills are pre-written `.md` files loaded into Bob sessions as system-context. One skill per specialist:

| Skill File | Specialist |
|---|---|
| `skills/code-impact-analyst.md` | Code Impact Analysis |
| `skills/test-engineer.md` | Test Engineering |
| `skills/security-analyst.md` | Security Analysis |
| `skills/api-compat-analyst.md` | API / Compatibility |
| `skills/doc-analyst.md` | Documentation Analysis |
| `skills/release-engineer.md` | Release Readiness Report |
| `skills/repo-understander.md` | Repository Understanding |

## 8. Recommended Bob Rules

Rules are placed in `.bob/RULES.md` (or equivalent Bob rules config) and apply to all Bob sessions in this project.

```markdown
## ForgeGuard Rules

1. EVIDENCE OVER CLAIMS — Never say a test passed unless the actual test runner output 
   is included. Never fabricate file contents, test names, or analysis results.

2. STRUCTURED OUTPUT — When asked to produce JSON, wrap it in:
   --- FORGEGUARD:JSON ---
   { ... }
   --- END ---
   Do not add commentary inside the JSON block.

3. SEPARATE FACTS FROM RECOMMENDATIONS — Use "OBSERVED:" for things seen in the code
   and "RECOMMENDATION:" for AI suggestions. Never blend them.

4. MINIMAL CHANGES — Make the smallest change that solves the problem. Do not refactor 
   unrelated code. Do not add unrequested features.

5. REPRODUCIBILITY — Always include the exact commands run and their full output.
   Never paraphrase command output.

6. AUDIT TRAIL — Begin every response with a one-line summary of what was done, 
   followed by evidence.

7. NO OVER-ENGINEERING — Do not propose abstractions, design patterns, or architectural 
   changes unless the issue explicitly requires them.

8. ROLLBACK AWARENESS — Before modifying any file, confirm the rollback reference 
   (git stash or branch) is established.
```

## 9. Recommended Reusable Skills

Each skill is a Markdown file that serves as a specialized system prompt for a Bob session.

### `skills/repo-understander.md`
Instructs Bob to:
- Map the directory structure
- Identify entry points, modules, and dependencies
- Return a structured repo summary (tech stack, key files, test framework)

### `skills/code-impact-analyst.md`
Instructs Bob to:
- Given a repo summary + issue, identify which files/functions are affected
- Trace call graphs and dependency chains
- Return: affected files, change scope (small/medium/large), blast radius

### `skills/test-engineer.md`
Instructs Bob to:
- Identify existing tests covering affected code
- Find gaps: code paths with no test coverage
- Recommend new test cases (names + descriptions, not implementations)

### `skills/security-analyst.md`
Instructs Bob to:
- Check if the change touches authentication, authorization, input handling, secrets
- Flag OWASP Top 10 relevant patterns
- Return severity (info/low/medium/high/critical) + evidence (file:line)

### `skills/api-compat-analyst.md`
Instructs Bob to:
- Identify public API surfaces (exported functions, REST endpoints, CLI flags)
- Flag breaking vs. non-breaking changes
- Check semver implications

### `skills/doc-analyst.md`
Instructs Bob to:
- Find documentation that references affected components
- Flag stale or missing doc coverage
- Return a list of doc files to update

### `skills/release-engineer.md`
Instructs Bob to:
- Aggregate all specialist findings + validation results
- Assign a readiness status: ready / conditional / not-ready
- Produce a human-readable release checklist with evidence refs

```
Phase 1 (sequential):  RepoUnderstander

                       (all five launched simultaneously via Promise.all)

Phase 7 (sequential):  ReleaseReporter
```

The parallel phase is the most visible Bob demonstration. The UI shows five cards animating simultaneously, with real-time progress and individual completion times — making it immediately clear that Bob is running parallel workstreams.

## 12. Testing Strategy

### Demo-app tests (the target codebase)

The `demo-app/` is a small Node.js/TypeScript utility library with:
- ~5 modules with clear single responsibilities
- ~20 unit tests using Vitest
- Intentional bugs and missing tests (for ForgeGuard to find)
- A small Express API endpoint (for API compatibility checks)
- A README (for doc analysis)

This is purpose-built to make every ForgeGuard analysis phase produce interesting, non-trivial output.

### ForgeGuard backend tests

- Unit tests for prompt-template construction
- Unit tests for JSON extraction from Bob responses
- Integration test for the pipeline phases (with Bob responses mocked)
- End-to-end smoke test: submit issue → receive Release Report (Bob live, short timeout)

### Validation commands (run by Bob in Validator phase)

```bash
cd demo-app && npm run lint     # ESLint
cd demo-app && npm test         # Vitest
cd demo-app && npm run typecheck # tsc --noEmit
```

All output is captured verbatim and stored as EvidenceItems.

## 13. Demo Scenario

Two pre-scripted scenarios are available in the UI as "Quick Load" buttons.

### Scenario A — Bug Fix

**Issue:** "The `calculateDiscount()` function returns incorrect results when discount rate exceeds 100%. It should clamp the rate to [0, 100]."

**Expected pipeline output:**
- RepoUnderstander maps `demo-app/src/pricing.ts` and related files
- CodeImpactAnalyst identifies `calculateDiscount()` + caller `applyOrderDiscount()`
- TestEngineer finds the existing test does not cover boundary cases
- SecurityAnalyst flags no security implications (low severity)
- ApiCompatAnalyst confirms function signature unchanged (non-breaking)
- DocAnalyst finds `README.md` mentions this function
- Plan: add input clamping + add boundary tests + update README
- Implementation: 3-line fix + 2 new test cases + 1 README sentence
- Validation: all tests pass
- Release Report: Ready, Low Risk

### Scenario B — Feature Addition

**Issue:** "Add a `formatCurrency()` function to the utils module that formats a number as USD currency string."

**Expected pipeline output:**
- New function added to `demo-app/src/utils.ts`
- New tests added
- API compatibility: new export (non-breaking, minor version bump recommended)
- Docs: README updated with new function description
- Release Report: Ready, Low Risk

## 16. Features NOT to Build

The following are explicitly out of scope for the 48-hour MVP. Do not implement them.

| Feature | Reason excluded |
|---|---|
| Multi-repository support | Complexity, not needed for demo |
| User authentication / login | No multi-user scenario in demo |
| GitHub / GitLab webhook integration | API rate limits, scope creep |
| Real PR creation | Git push access complexity |
| Support for non-JS/TS target repos | Demo app is JS/TS; keep it simple |
| LLM model selection UI | Bob handles model selection |
| Custom rule editor in UI | Rules are .md files; editor is overkill |
| Skill editor in UI | Same reason |
| Persistent cloud database | SQLite is sufficient for demo |
| Docker containerization | Dev environment is sufficient |
| CI/CD pipeline for ForgeGuard itself | Not needed for hackathon |
| Mobile / responsive below 1024px | Demo is on a laptop |
| Internationalization | English only |
| Accessibility audit | Out of scope for hackathon |
| Performance optimization / caching | Demo scale is tiny |
| Multiple concurrent runs | Single-run demo is sufficient |
| Configurable Bob model parameters | Not needed |
| Webhook notifications | Out of scope |
| Export to PDF | Judges view in browser |
| Test coverage reporting (Istanbul/NYC) | Vitest built-in is enough |
